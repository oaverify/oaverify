3 rule(s) in this report explained:

  format-not-validated: a format name with no validator behind it
    Values carrying this format are checked against "type" alone. That is legal:
    support for any given format is optional, and a validator may fall back to
    "type" for one it does not recognise. Register a validator for the name
    through the formats option to enforce it, or read this finding as
    confirmation that the name is documentation rather than a constraint.

  example-invalid: an example the schema it illustrates rejects
    Every example in the document is validated against the schema it sits in. An
    example reached through a $ref is checked once at the component that
    declares it rather than at each use site, so one finding can stand for many
    references. The message names up to five distinct reasons and then counts
    the rest; the finding's reasons field carries every rejected leaf, uncapped
    and unabbreviated.

  ambiguous-pattern: a pattern whose matching can blow up on crafted input
    A backtracking engine can be made to explore every way an ambiguous pattern
    matches, so an input crafted against it can take superlinear time. Whether a
    given pattern actually costs that depends on the engine running it, which is
    not known here. Rewrite the pattern to remove the ambiguity, or compile
    patterns with a linear-time engine through the regexCompiler option.
